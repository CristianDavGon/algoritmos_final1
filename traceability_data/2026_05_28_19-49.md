## Contexto y objetivo

El propósito es comparar, para diferentes grupos de nodos (hasta **15 nodos**), los resultados obtenidos por **QNodes** y **GeoMIP** frente a los generados por **PyPhi**.

A partir de esta comparación, se deben generar **métricas cuantitativas** que permitan:

* Medir qué tan cerca o lejos están los resultados de **QNodes** y **GeoMIP** respecto al resultado de referencia (**PyPhi**).
* Evaluar el desempeño general del proyecto en términos de precisión, consistencia y calidad de los resultados.
* Facilitar comparaciones entre métodos bajo diferentes configuraciones de entrada.

## Alcance actual y extensibilidad

Inicialmente, las pruebas deben implementarse para **biparticiones**. Sin embargo, el diseño debe ser **modular y extensible**, de modo que en el futuro sea sencillo adaptar la lógica para soportar **k-particiones (k > 2)** sin requerir una reestructuración significativa del sistema.

## Requisitos funcionales de las pruebas

Las pruebas deben ser **dinámicas**, siguiendo el mismo enfoque con el que actualmente se ejecutan los métodos del proyecto. En particular:

* Debe ser posible indicar dinámicamente la **cantidad de elementos/nodos** a evaluar.
* Las pruebas deben ejecutarse utilizando las **TPM de ejemplo (simples)** que ya posee cada proyecto.
* La ejecución debe permitir correr automáticamente los métodos **QNodes**, **GeoMIP** y **PyPhi** sobre los mismos escenarios de prueba para garantizar comparabilidad.

## Optimización de ejecución con PyPhi

Dado que **PyPhi es computacionalmente costoso**, se debe implementar un mecanismo de **persistencia y reutilización de resultados** para evitar recalcular escenarios ya procesados.

Los resultados de referencia generados por **PyPhi** deben almacenarse en una estructura similar a:

`tests/data`

o una carpeta equivalente destinada al almacenamiento de datos persistentes de pruebas.

Cada vez que se ejecute un test, el sistema debe:

1. Verificar si ya existen resultados previamente calculados para la combinación específica de:

   * Número de nodos.
   * TPM utilizada.
   * Sistema/subsistema evaluado.
   * Configuración de prueba correspondiente.

2. Si los resultados ya existen, reutilizarlos directamente en lugar de volver a ejecutar **PyPhi**.

3. Si no existen, ejecutar **PyPhi**, generar los resultados y persistirlos automáticamente para futuras ejecuciones.

Esto permitirá reducir significativamente los tiempos de prueba y evitar cálculos redundantes.

## Arquitectura y adaptadores

Se debe analizar si es necesario implementar un **método o capa de abstracción adicional**, considerando que actualmente **cada grupo/sistema utiliza un adaptador específico para PyPhi**.

El diseño debe garantizar:

* Una integración limpia con los adaptadores existentes.
* Reutilización de lógica común.
* Bajo acoplamiento entre estrategias (**QNodes**, **GeoMIP**, **PyPhi**).
* Facilidad para extender el sistema a nuevas estrategias o tipos de partición en el futuro.

## Gestión de resultados

Los resultados deben generarse y almacenarse de forma **dinámica y organizada** dentro de una carpeta dedicada a pruebas, por ejemplo:

`code/tests/results`

El almacenamiento debe permitir:

* Persistir los resultados de cada ejecución.
* Facilitar comparaciones posteriores entre métodos.
* Mantener una estructura clara y escalable para futuras pruebas y nuevas métricas.
* Diferenciar resultados según número de nodos, TPM utilizada y método ejecutado.

### respuesta
Se diseñó e implementó la suite de pruebas completa en `code/tests/` para comparar QNodes y GeoMIP contra PyPhi como baseline.

**Arquitectura implementada:**
- `models.py` — dataclasses compartidos: `TestCase`, `PartitionResult`, `RunRecord`, `BenchmarkReport`
- `cache.py` — `PyPhiCache`: caché JSON write-through en `code/tests/data/pyphi_cache.json`, con clave `{n}|{page}|{estado}|{alcance}|{mecanismo}`
- `excel_loader.py` — `cargar_casos()`: lee `DatosPruebas2026_1.xlsx` y convierte letras a máscaras binarias
- `metrics.py` — `compute_run_record()`, `agregar_reporte()`: cómputo puro de phi_delta, phi_match, partition_match, speedup
- `reporter.py` — `guardar_csv()`, `imprimir_resumen()`: escritura a `code/tests/results/`
- `adapters/base.py` — ABCs `StrategyAdapter` y `PyPhiAdapter` con interfaz uniforme `run(test_case, tpm) → PartitionResult`
- `adapters/qnodes_adapter.py` — `QNodesAdapter` + `QNodesPyPhiAdapter`: maneja `sys.path`, singleton `aplicacion.set_pagina_red_muestra()` + `desactivar_profiling()`
- `adapters/geomip_adapter.py` — `GeoMIPAdapter` + `GeoMIPPyPhiAdapter`: maneja `aplicacion.pagina_sample_network` + `profiler_habilitado = False`
- `runners/benchmark.py` — `BenchmarkRunner`: Template Method que orquesta cache → PyPhi → estrategia → métricas → CSV
- `test_qnodes_vs_pyphi.py` / `test_geomip_vs_pyphi.py` — entry points configurables con constantes al tope (ESTADO_INICIO, PAGINA, N_TESTS, TOL_PHI)

**Restricción crítica:** ambos módulos usan `src.*` como raíz de paquete. Se deben ejecutar en procesos pytest separados.

**Extensibilidad k-particiones:** agregar una nueva estrategia = crear un `StrategyAdapter` nuevo. `_particiones_iguales()` en `metrics.py` es el único punto a actualizar para soporte de k > 2.
